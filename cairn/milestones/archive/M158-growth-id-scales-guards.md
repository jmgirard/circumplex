# M158: Merged-id and repeated-scale guards for ssm_growth_data()

**Status:** done (2026-10-17, PR #193 https://github.com/jmgirard/circumplex/pull/193)

**Goal:** `ssm_growth_data()` refuses two inputs that today give a wrong long table with no error: distinct `id` values that become one person in the output, and `scales` that select one column more than once.

**Outcome:** Two `stop(call. = FALSE)` guards in `R/ssm_growth_data.R`, before the unchanged scoring and stacking. (1) Merged ids: when `nlevels(factor(id_col))` is below `length(unique(id_col))`, the error gives the positions (not row names) of one pair and the label they share (`0.1 + 0.2` and `0.3` share "0.3"; complex ids too). It runs after the infinite-time check and before the repeated-row check, so a same-time merged pair gets this message, replacing M157's "more than one row" assertion for that pair. `0` and `-0` are one value and pass. (2) Repeated scales: names judged by name, only those present in `data`; numbers by `seq_along(data)[scales]`, so `3` and `3.5` both reach PA. It runs after the id/time selection checks, so `c("person", "person", ...)` keeps the id message. An `NA` or absent name and a number reaching no column go on to the scorer's "undefined columns selected". Four test blocks in `tests/testthat/test-ssm_growth_data.R`; the help page's `data` and `scales` text and the NEWS refusal list name both refusals.

**Decisions:** none milestone-local. Error over warning for merged ids on GP2's wrong-object clause, as M157's repeated-row refusal; the cross-scorer repeated-scale guard stays on the "Growth id and scales edge inputs" row.
